- [x] **5. Automatyczny deploy przez Cloudflare.** Workers Builds połączono z `WjchLLK/obiadek` i gałęzią `master`; Build command `npm ci && npm run build`, Deploy command `npx wrangler deploy`, root `/`, `SKIP_DEPENDENCY_INSTALL=1`. GitHub Actions wykonuje testy, nie deploy. Sekrety Supabase pozostają runtime secrets Workera. Pierwszy build i logowanie po deployu potwierdzone.
  Workers Builds automatycznie wygeneruje token użytkownika o szerokich domyślnych uprawnieniach (m.in. Workers Scripts, KV, R2 oraz Workers Routes dla wszystkich stref). Właściciel przed połączeniem przegląda API token w ustawieniach Build i wybiera lub tworzy token user-scoped z możliwie wąskim dostępem; integracja obecnie obsługuje tokeny użytkownika, nie account-owned. Ogranicz autoryzację aplikacji GitHub do tego repozytorium, jeśli instalator to umożliwia. Nie zatwierdzaj automatycznie szerokiego tokenu bez akceptacji zakresu przez właściciela. Workers Builds po pushu do produkcyjnej gałęzi uruchamia build, po czym deploy; **nie czeka na GHA**. Dlatego ochrona `master` musi wymagać PR, ludzkiego zatwierdzenia i zielonych wymaganych GHA `ci` oraz `smoke`; wyłącz bypass push/administratora, jeśli ustawienia GitHub to umożliwiają. Gdy nie można wymusić wymaganych kontroli, nie włączaj auto deployu.
  Zweryfikuj gałąź produkcyjną, uprawnienia/token, wersję Node/npm i pełny log pierwszego buildu przed uznaniem integracji za gotową. Poświadcz, że tylko push do `master` publikuje produkcję.
